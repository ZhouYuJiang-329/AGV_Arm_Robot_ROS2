# 定位诊断与TF时间接入修复

本轮修复两项已复现的软件问题：正常等待odom插值不再使有效定位立即失效；Nav2能够在原定位有效期内，用新鲜odom获得足够的map→odom时间支持。
没有放开运动、坐标确认或输入采样时间确认开关，没有发送速度、实际导航目标、重定位或控制权操作。

## 根因和复现

1. 原节点只有一组状态。新定位响应等待后一侧odom样本时，把`tf_available`清为false、把定位`fresh`清为false。
   尽管上一份接受的定位仍新鲜，诊断却发出`level=2 / waiting_for_odom_bracket`，停止保护按其合同拒绝该输入。
   新的`localization_timing_test`通过真实ROS节点和受控数据源复现，原实现稳定报错“normal interpolation wait invalidated a still-fresh accepted localization”。
2. 原map→odom仅在2Hz绝对定位接受时发布，扫描为5Hz。部分扫描需要尚未发布的后一侧map→odom支持点，超出Nav2过滤器300ms的等待期限。
   本机Jazzy的MessageFilter对TF等待future的异常统一映射为OutTheBack，因此日志虽然写“早于缓存”，也可能实际是等待将来的变换超时，不能据此直接增大缓存。
   新的`localization_scan_filter_test`使用真实tf2 Buffer和MessageFilter、同样的双目标frame、50ms扫描tolerance和300ms等待，在单发布者/固定挂载/单调时间下重现相同日志。
   原实现20帧扫描只接纳8帧，说明无需无线网络故障、时钟跳变或重复TF发布者也能复现。

只修诊断状态时，第一个测试越过正常等待断言，随后在缺少新odom时间支持处失败；过滤器仍为8/20。
加入有界TF支持后，过滤器为20/20。这一分步结果把两个根因区分开，没有靠一起改参数来猜原因。

接口核对：[Nav2 Jazzy障碍层](https://github.com/ros-navigation/navigation2/blob/jazzy/nav2_costmap_2d/plugins/obstacle_layer.cpp)、
[tf2 Jazzy消息过滤器](https://github.com/ros2/geometry2/blob/jazzy/tf2_ros/include/tf2_ros/message_filter.hpp)。实际复现使用本机已安装头文件/库。

## 改动与时间合同

`robot_move/localization`分别保存待处理样本和已接受样本：

- 新样本正常等待odom包围时，以`pending_reason=waiting_for_odom_bracket`报告处理进度。
- 已接受样本只有在自身仍新鲜、最新odom仍新鲜且没有质量/查询/TF所有者故障时，才继续保持原有有效状态。
- 错地图、低质量、查询失败、跳变隔离等仍立即拒绝；odom过期或原定位过期也立即失效。
- `response_age_sec`严格由诊断原header时间减去**已接受Pose的原接收时间戳**计算；新查询、定时器和TF发布均不重置它。
- 新增`accepted_pose_stamp_sec`、`pending_reason`、`tf_support_stamp_sec`、`tf_publish_mode`诊断，区分观测时间和TF支持时间。

新增只读参数`tf_publish_mode`：

| 值 | 行为 |
| --- | --- |
| `measurement_time` | C++构造默认值，保留兼容模式：每个新接受查询发布一次同时间戳Pose与TF |
| `bounded_odom_hold` | 实机YAML明确选择：Pose仍只发布一次原时间戳；在原定位有效期内，为新鲜odom时间提供map→odom支持 |

后一模式不是给旧绝对Pose重盖时间戳。先按原定位时刻精确插值，得到校正量：

`T_map_odom = T_map_base(定位时刻) × inverse(T_odom_base(同一时刻))`

在下一次合格定位到来前，只在收到新鲜odom样本时使用这份有界校正；此时预测的map→base仍由新的odom决定。
TF时间戳取**已经收到的odom样本时间**，严格递增，既不取发布时now()，也不发布未来TF。不会重发已接受的Pose消息。
新校正应用于下一条可用的递增odom支持时间，不向已发布时间范围倒插新的变换。

保护仍检查原定位诊断的样本年龄，不能因为TF不断更新而延长原定位寿命。`max_sample_age_sec=0.8`、`max_odom_age_sec=0.5`、
查询上限、插值上限、双雷达期限均未放宽；实际代价地图`transform_tolerance`仍为0.3s。
实机执行门禁同时读取运行中的`tf_publish_mode`，要求为`bounded_odom_hold`，避免旧节点/自定义参数遗漏该接入策略。
默认坐标确认仍false，`coordinate_status=UNVERIFIED_ASSUMPTION`仍会阻止实机执行。

## 当前边界

本轮定位诊断误失效和TF时间支持不足两个问题已通过离线回归与该窗口的实机只读复验。
这仍不是实际运动放行：坐标/外参、机械臂锁定包络、设备内部采样时间/缓存契约及固件到期/实际故障停车尚需验收。
下一步应在现场核对现有轮廓和障碍代价，完成确认后再另行授权低速短距离运动。

预防这类回归的关键是分别记录观测是否仍有效、新样本处理进度和TF支持时间，并用真实过滤器测试稀疏定位/高频扫描的组合及过期拒绝路径。
